代码在 `datagen/`（用法和各门的定义见 `datagen/README.md`）；三批各 50 个场景的输出在 `~/vlmg-data/datagen/{test50,test50b,test50c}/`，人工审核页在 `review/<run>/index.html`（Windows 侧，已 gitignore）。**请审 `review/test50c/index.html`**：每张卡片左边是图（绿框 T = 目标，橙框 S = 兄弟，灰框 = 其他候选，红/紫/蓝细框 = 基座在 e_T / e_T⁻ / e_S 下的输出框，圆点 = Molmo2 指点），右边是三句表达式、细节 × 候选的核对矩阵（含第二核对者一列）、基座输出、听者结果和门的通过情况。

## 1. 流水线做了什么

一个源场景（OpenImages 图 + SAM 3 实例，同类 ≥3）→ 一条主记录：

| 阶段 | 模型 | 产出 |
|---|---|---|
| select | — | 整物体类、目标不小于 1% 图面、不贴边、候选去重去嵌套 |
| write | Qwen3.5-9B（画红框全图 + 目标放大裁剪） | 目标描述 e_T（4–7 个细节）、原子拆解、改假一个细节的 e_T⁻（模型给出原词与三个候选新值，替换由代码做） |
| policy | Qwen3-VL-8B（GroundingME 原 prompt，逐字节） | 框、决策 token 的 p(null)/p(box)、框落在哪个候选上 |
| sibling | Qwen3.5-9B | 兄弟描述 e_S（基座在 e_T 下框错的那个实例；否则最大的兄弟） |
| blind | Qwen3.5-9B 纯文本 | 不看图能否猜出被改的句子 |
| check | Gemma4-12B（画框全图 + 放大裁剪） | 每个细节 × 每个候选 yes/no；改假细节在每个候选上是否为 no |
| check2 | Qwen3-VL-8B | 目标行的第二意见 |
| listen | Molmo2-8B（**必须在 `~/molmo-env`，transformers 4.57**） | 只看描述指目标；逐条删细节再指（承重率） |
| report | — | records.jsonl、gates.md、审核页 |

## 4. 我自己的检查结论

- 机制层面全部跑通：三家模型各司其职，断点续跑有效（两次遇到 WSL 的瞬时 CUDA 错误，重跑同一命令即接上）。
- 我看了 9 张图。写手在头名词正确、目标清楚时写得很好（雕像、海报、篝火旁的人、企鹅这几条全门通过的样本，描述、兄弟描述和改假都干净）。失败集中在三处：类别名错（已修）、目标被更大同类物体遮挡/包含（已修）、1024 px 上的小物体细节（未修，要原图分辨率）。
- **负样本的瓶颈是核对者太严**：Gemma4 对我肉眼确认成立的细节（"坐在摩托车的挎斗里""坐在蓝色敞篷车驾驶座"）说 no；目标行 yes 率 73%，兄弟行 31–37%，说明它能区分但偏保守。第二核对者（Qwen3-VL-8B）与它在目标上一致率 62%。"全部 yes" 这道门因此只放过 26%。
- **改假值有一半落在兄弟身上**（"红苹果"图里另一个苹果正好是红的）。核对者正确地把它们拦下了（这正是它的用途），但产出因此减半；三个候选新值已经生成，下一步让核对者按顺序试到第一个零满足为止。
- **改假在文本上可被识别**（判官 67%，随机 50%）：需要 SugarCrepe 式"判官猜得出就重生成"。
- **候选清洗让题变容易了**：基座框错率从 42–52% 降到 20%，困难正样本一条都没剩。困难正样本需要另一个来源（保留一部分重叠场景，或用 SA-1B 原图）。
- 承重率 18% 说明写手写的是 GroundingME 那种"多数从句是装饰"的长描述，对负样本合适；正样本训练时要注意。

## 8. Gemini 3.1 Pro 作核对者、放大裁剪校正、改假 bug（2026-09-22 下午）

**放大裁剪推翻了我 4 个"写手编造"的判断**（#2 悍马、#11 小银车、#37 鞋底红图案、#49 青铜罐）：写手看的是放大裁剪，我在 1024 px 整图上看不见那些细节。这一批写手真正写错的只有 #5（金属球）。审核页每张卡片现在都附每个候选的放大裁剪（`render_sheet`）。复核后：可用 20、存疑 4（#2、#4、#11、#27）、不可用 26。

**流水线 bug**：#5、#22、#47 三个场景里模型按 v1 格式回了整句 + `CHANGED:`，新值被追加在句尾而不是替换，代码回退时把原句那条当成"改假条目"送去核对，于是核对者"判目标满足改假值"。修法：`substitute_once` 改成整词匹配（`red` 不能命中 `covered`）；新值包含原短语的丢弃；改假条目与原句相同则记为 `flip_failed`；`changed_to` 与实际生成负句的新值对齐。

**Gemini 3.1 Pro 核对者**（`datagen/checker_api.py`，`check --checker gemini`，`report --primary-checker gemini`）：同一 prompt、同样 1,283 次核对，6 路并发 14.7 分钟，2.95M 输入 token ≈ 6.4 美元（每场景 0.13 美元；全分辨率放大裁剪的 tile 比预想多）。`max_output_tokens=64` 时 16% 回答为空（思考 token 占掉预算），已改 512 并补跑。

Gemini 与 Gemma 目标行一致率 81%。Gemini 仍拦下的 9 个可用样本：6 个是它对某一条成立的细节说 no（#7 圆头灯、#10 胸口白斑、#13 萼片数（写手确实数错）、#28 坐在沙地上、#29 调料罐、#37 连帽衫/坐姿措辞），2 个是零满足门（#22 是上面的 bug，#44 它误放"持剑"），1 个是听者漏指（#42）。Gemini 的毛病是空间关系偏宽松（#5 两条假的都说 yes；#25 五条全 yes 倒可能是对的）。

## 9. PoC 数据集：poc155 全流程 + 两轮审核（2026-09-22 晚）

`poc155` = 当前 select 规则下池子里除 test50c 外的全部 155 个场景（per-label 不封顶，Person 43、Car 33）。链条 `scratchpad/chain_poc.sh`：写手 → Gemini 合并核对 → 基座 → 兄弟 → 判官 → 听者 → Gemma4 → 第二核对者 → 报告，本地约 2.5 小时，Gemini 约 6 美元。

**reflip 两轮。** 第一轮（`datagen/reflip.py`：先试写手备选值，再重新生成两次，每个候选用 Gemini 按整句核对）54 个场景 53 个接受，但语法门拦下 23 个，多为自相矛盾（关系换成了新属性）；审核后又有 34 个原写手的改假被判为矛盾/病句。第二轮改成只允许改"值"（对齐后的核心 ≤3 词、词数变化时必须共享首尾词），对 57 个改假失败场景强制重试（`reflip_force.txt`），54 个接受，复审后 39 个可用。根因是模型按"从句形式"回答 OLD/NEW（"has a white car parked nearby"），代码现在用 `common.align_span` 对齐到表达式里的实际片段，这也进了写手。
